Sparse irregular datacubes · FAO dekadal & pentadal calendars

Which periods actually have data here?

A GeoZarr store carries its own time coordinates. A cube made of thousands of separate COG files does not: no single file knows the whole axis, and most calendar periods have no file at all for a given area (cloud masks, late ingestion, partial swaths). A map client has to answer one question before it draws a time slider or reads a pixel: of all the periods the calendar defines, which ones have data inside my area? This workbench answers it in three steps against real sparse fixtures for January 2021.

D · the calendar

Every period the calendar defines, with its real start and end. Pentadal = 72 per year (P6 runs from day 26 to month end); dekadal = 36 per year (D3 runs from day 21 to month end). Same for every place on Earth.

S(AOI, Δt) · what exists here

The subset of D for which at least one COG granule intersects your area and time window. It changes when you pan the map.

D \ S · the gaps

Periods to grey out in the UI and to skip when extracting. Without knowing them, a client reads empty slices blindly.

Step 1 · Read the calendar D

The calendar is published once as a dimension resource and linked from the STAC collection through cube:dimensions.time.definition. It is cacheable and independent of any file.

Common Part 2 UAD (draft) · Records items

The 2021 pentadal calendar

Which pentads does 2021 have, and where does each one start and end?

Expect 72 matched; first page shows Jan and Feb P1–P6. Jan P6 lasts 6 days, Feb P6 only 3.

CQL2 T_INTERSECTS · OGC 21-065r2

January, as pentads

Which pentads overlap January 2021?

Expect P1–P6. This is the full set D for the window used below.

datetime parameter

January, as dekads

Which dekads overlap January 2021?

Expect D1–D3; D3 covers 21–31 (11 days), so no fixed ISO 8601 step fits.

Step 2 · Find what exists here S(AOI, Δt)

The granule footprints are indexed (GeoPackage R-tree here; STAC, GeoParquet or DuckDB elsewhere). A spatial filter on the collection's /items prunes empty periods on the server. The last three cards ask for the answer as a CoverageJSON Domain: only the populated time values, in well under a kilobyte.

EDR /items + Features Part 3 filter

South-west area, as footprints

Which granules intersect a small area near 12.0–12.5°E, 39.0–39.5°N in January?

Expect 3 GeoJSON features: P1, P3, P6. P2, P4, P5 were never ingested.

Proposed EDR extension · Domain on /items

South-west area, as a Domain

Same question, but return only the populated time values with their bounds.

Expect t = P1, P3, P6, each with its [start, end].

Proposed EDR extension · Domain on /items

North-east area: the answer changes

Move the area to 13.5–14.5°E, 40.5–41.5°N. Does P3 still have data?

Expect t = P1, P6. The P3 granule only covers the south-west, so P3 drops out. A global collection summary would wrongly list it.

Proposed EDR extension · Domain on /items

Dekadal cube, January

Which January dekads have any granule?

Expect t = D1, D3; D2 is a deliberate gap.

What is standard today and what is proposed. Green badges are published OGC standards. Blue badges compose published pieces (OGC API – Common Part 2 UAD is still a draft; EDR /items defers its filtering to OGC API – Features, so the CQL2 filter parameter comes from Features Part 3 rather than from EDR itself). Amber badges are the extension this demo proposes to the EDR Standards Working Group: a CoverageJSON Domain response listing only the populated periods.
